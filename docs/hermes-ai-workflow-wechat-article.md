# AI界里全自动工作流的“爱马仕”：Hermes 怎么把 Claude、Codex、Kimi K2.6 装进同一个工作台

很多人现在用 AI，其实像在开一排窗口。

一个窗口问 Claude。

一个窗口让 Codex 改代码。

一个窗口丢给 Kimi 长跑。

还有一个窗口开着浏览器、终端、公众号后台、Notion、Obsidian。

看上去很高级。

但说实话，这种用法越久越累。

你不是在指挥一个 AI 团队，你是在当 AI 团队的人工路由器。

这也是我最近重新看 Hermes 的原因。

Hermes 这个名字起得很妙。它不是最强的模型，也不是某一个聊天框，而更像 AI 世界里的“爱马仕工作台”：把 Claude、Codex、Kimi K2.6、工具、技能、记忆和发布动作放进同一个操作系统里。

当然，名字有点贵气。

但真正贵的不是它的名字，而是它解决的问题：

> 你不需要再问“哪个模型最强”。
>
> 你要问的是：哪件事，应该交给哪个 agent。

✦ ✦ ✦

## 一、别再让一个模型包打天下

我现在越来越不相信“一模走天下”。

不是模型不够强。

而是任务不同，脑子就应该不同。

写一个公众号标题，和重构一个 React 项目，不是一回事。

读 30 篇资料做选题，和在 Git 仓库里跑测试修 bug，也不是一回事。

如果全部压给一个模型，它当然也能做。

但结果往往是：能做，不够稳；能写，不够像你；能改，不一定知道为什么改。

所以 Hermes 的思路更像一个调度层。

它不是把 Claude、Codex、Kimi K2.6 变成一个“超级聊天机器人”，而是把它们放进各自擅长的位置。

| 角色 | 最适合做什么 | 不适合做什么 |
| --- | --- | --- |
| Hermes | 总控、技能调用、工具编排、记忆、跨阶段工作流 | 单独承担所有深度判断 |
| Claude | 架构判断、复杂问题拆解、重构风险、长文质量把关 | 高频低成本长跑 |
| Codex | 写代码、改文件、跑测试、修 CI、做 PR review | 泛泛聊天、长期内容运营 |
| Kimi K2.6 | 长上下文、低成本多轮执行、批量任务、agent 长跑 | 需要极强审美或极精细判断的最终定稿 |

这张表很重要。

因为很多 AI 工作流失败，不是模型差。

是你让它干错了岗位。

## 二、Hermes 到底放在哪个位置？

我的理解很简单：

Hermes 不是“又一个 AI”。

Hermes 是一个工作台。

它负责把这几件事串起来：

- 读项目
- 调模型
- 调工具
- 调技能
- 保存记忆
- 执行命令
- 触发发布
- 记录结果

这就像你开公司。

Claude 是总工。

Codex 是工程师。

Kimi K2.6 是能长时间干活的执行同事。

Hermes 是那个把任务派下去、把文件收回来、把结果送到下一环的人。

以前我们是人肉做这件事。

现在可以让 Hermes 做一部分。

注意，我说的是一部分。

完全自动不是上来就全自动。真正靠谱的自动化，一定是从一条稳定的小流水线开始。

比如：

> 采集资料 → 选题 → 初稿 → 人审 → 母版 → 插图 → 公众号排版 → 草稿箱

这条链路比“帮我写篇爆款文章”高级太多了。

也更接近真实生产。

## 三、我建议的默认组合

如果你刚开始折腾，可以先别搞复杂。

就按这个组合来：

| 场景 | 推荐组合 |
| --- | --- |
| 日常主控 | Hermes + Kimi K2.6 |
| 架构分析 | Hermes 调 Claude |
| 代码落地 | Hermes 调 Codex |
| 长任务执行 | Hermes + Kimi K2.6 |
| 内容母版打磨 | Claude 把关，Kimi 执行 |
| 公众号草稿箱 | Hermes 调本地脚本 |

这样分工的好处是，成本和质量都能平衡。

Kimi K2.6 负责长跑，不心疼。

Claude 负责关键判断，不浪费。

Codex 负责动代码，不飘。

Hermes 负责把这一堆动作串起来，不让你来回复制粘贴。

## 四、安装 Hermes，先让工作台跑起来

如果你还没装 Hermes，可以先从最小安装开始。

```bash
curl -fsSL https://raw.githubusercontent.com/NousResearch/hermes-agent/main/scripts/install.sh | bash
```

刷新 shell：

```bash
source ~/.zshrc
```

启动：

```bash
hermes
```

常用命令不用记太多，先记这几个：

```bash
hermes setup
hermes model
hermes tools
hermes doctor
hermes update
```

我的建议是，第一次不要急着配一堆插件。

先做一个最小测试：

```text
请只读当前项目，告诉我：
1. 这个项目是做什么的
2. 技术栈是什么
3. 哪些目录最重要
4. 不要修改任何文件
```

能稳定完成这个，才进入下一步。

否则后面你接 Claude、Codex、Kimi，只会把混乱放大。

## 五、把 Kimi K2.6 放在 Hermes 主模型上

我会把 Kimi K2.6 放在 Hermes 的日常主模型位置。

原因很现实：

Hermes 这种 agent 工作台，最常做的不是一次性回答，而是长时间、多步骤、反复读写上下文。

这类任务如果全部交给昂贵模型，你会舍不得跑。

如果交给太弱的模型，又容易跑偏。

Kimi K2.6 比较适合承担这个“长跑位”。

配置时可以走：

```bash
hermes setup
```

如果你的服务商提供 OpenAI-compatible API，大概会填这些东西：

```text
Provider: custom
Endpoint: https://你的-api-endpoint/v1
API Key: 你的 API Key
Model: moonshot/kimi-k2.6
```

这里有个小坑。

不同服务商的 model id 不一定一样，endpoint 末尾要不要 `/v1` 也不一定一样。

别凭感觉写。

以你实际 API 服务商后台为准。

配置完以后，让 Hermes 做一个只读任务：

```text
请读取当前目录，输出项目摘要和可执行任务清单。不要修改文件。
```

如果这一步稳了，Kimi K2.6 的主控位基本就通了。

## 六、Claude 不要拿来干杂活，要拿来做判断

Claude Code 最适合做什么？

我的看法是：判断。

不是每次都让它直接改文件。

它适合看复杂项目，判断哪个问题值得修、哪个问题不能碰、哪个重构会引爆一堆连锁反应。

你可以让 Hermes 这样调用 Claude：

```text
请调用 Claude Code 分析这个项目的架构。

只读，不改文件。

重点看：
1. 数据流是否清楚
2. 模块边界是否混乱
3. 哪些地方适合交给 Codex 做最小修复
4. 哪些地方暂时不要动
```

这类任务交给 Claude，很值。

因为它不是在替你敲代码，而是在帮你少走错路。

很多时候，AI 改坏项目，不是因为代码写错了。

是因为一开始方向就错了。

Claude 适合把这个方向先拧正。

## 七、Codex 要当工程师用，不要当聊天工具用

Codex 的位置更像工程师。

你给它一个清晰边界，它就能改文件、跑测试、看报错、再改一轮。

不要这样说：

```text
帮我优化一下项目。
```

这句话太虚。

改成：

```text
请用 Codex 修复首页移动端布局。

范围：
- 只看 index.html、styles.css、app.js
- 不重构无关模块

验收：
- iPhone 宽度下按钮不溢出
- hero 首屏能看到下一段内容
- 不影响桌面端主要布局
- 修改后运行本地检查，并汇报改动文件
```

这样它就像一个工程师。

有范围。

有验收。

有回报。

也不容易顺手把半个项目都重写了。

## 八、真正好用的是“三段式工作流”

我现在比较喜欢这个节奏：

### Kimi 先读，建立上下文

```text
请阅读项目，输出：
- 项目目标
- 主要模块
- 当前最可能的技术债
- 适合交给 Claude 分析的问题
- 适合交给 Codex 执行的问题
不要修改文件。
```

这一步是让 Hermes 主模型先把地形摸清楚。

### Claude 再判断，决定动不动

```text
请调用 Claude Code 分析上一步列出的技术债。

输出：
- 优先级
- 为什么现在值得做
- 风险点
- 哪些不要动
```

这一步不是写代码，是防止乱动。

### Codex 最后执行，做最小修改

```text
请调用 Codex 执行优先级最高的一个修复。

要求：
- 改动尽量小
- 保留已有用户改动
- 修改后跑检查
- 最后汇报文件、原因、验证结果
```

这就顺了。

Kimi 建上下文。

Claude 定方向。

Codex 动手。

Hermes 串流程。

## 九、内容创作也可以这样跑

这套东西不只适合写代码。

拿公众号来说，也可以跑成一条更完整的内容流水线。

我本地看到的稳定方案大概是这样：

```text
09:00 Hermes 每日流水线
  采集资料
  生成选题
  写初稿

人工审核
  选出值得继续打磨的文章
  不合格的留在初稿池

10:30 发布管线
  生成插图
  上传微信素材
  Markdown 渲染成公众号 inline HTML
  推送到公众号草稿箱
  记录 appMsgId
  发通知
```

这条链路有个很关键的观念：

初稿不要直接发。

先进入筛选池。

这点特别重要。

因为 AI 很容易写出“看上去完整，实际上没劲”的文章。

如果直接自动推草稿箱，你会得到很多工整但平庸的内容。

更好的方法是每天多产几篇，先审核，再升级为母版。

母版通过后，再进入插图、排版、草稿箱。

## 十、公众号排版别用普通 Markdown

公众号排版有自己的脾气。

不是你写个漂亮 Markdown，它就会漂亮。

很多 CSS 在公众号里会被清洗掉。

比如：

- `<style>` 容易被剥离
- flex/grid 不稳
- 伪元素不稳
- 外链图片可能被清
- 本地图片路径肯定不行
- 复杂背景图不适合直接塞

所以更稳的办法是：

> Markdown 只是母版。
>
> 真正入草稿箱前，要渲染成公众号兼容的 inline HTML。

本地已经有一个很成熟的白底暗金杂志版方案。

它的特点是：

- 白底
- 暗金色强调
- 衬线字体
- H2 带章节感
- 表格可读
- 金句块独立
- 图片居中
- 全部 inline style

这种排版比“AI 生成的 Markdown 标题 + 列表”高级很多。

公众号读者看到的不是你的工作流，而是你的审美。

## 十一、推送公众号草稿箱的稳定路径

这部分有点技术，但很有价值。

官方 API 当然可以用。

但问题是 AppID、AppSecret、IP 白名单、素材上传、动态 IP，一堆配置下来，很容易卡死。

本地现在更稳的路径是：

> Chrome 保持登录公众号后台，然后通过 AppleScript 在已登录页面里执行 JS，调用公众号内部接口创建草稿。

这听起来有点野。

但它的好处是，不需要额外管理公众号 API 凭证。

只要你 Chrome 里已经登录 `mp.weixin.qq.com`，脚本就能拿到当前 session 里的 token，再把 HTML 推到草稿箱。

一键命令长这样：

```bash
bash ~/.claude/scripts/wechat-draft-from-md.sh <markdown路径> "标题" "摘要" magazine
```

如果想用五行自动配色：

```bash
bash ~/.claude/scripts/wechat-draft-from-md.sh <markdown路径> "标题" "摘要" wuxing
```

但这里有几个前置条件：

- Chrome 里必须已经登录公众号后台
- Chrome 要开启 `Allow JavaScript from Apple Events`
- 草稿必须带图，除非你明确说先推无图版
- 同一篇不要重复推，避免草稿箱出现多份

我觉得这条路很适合个人创作者。

因为它不是奔着“企业级内容中台”去的。

它奔着“一个人也能每天稳定产出、审核、排版、入草稿”去的。

这个差别很大。

## 十二、最容易踩的三个坑

### 1. 上来就追求全自动

别这样。

先跑半自动。

尤其是内容创作，一定要留人工审核。

AI 可以帮你写五篇初稿，但哪一篇值得发，最好还是你自己拍板。

### 2. 多个 agent 同时改同一批文件

这个很危险。

Claude 说要重构。

Codex 也在改。

Kimi 还在整理。

最后 diff 变成一团。

正确做法是拆责任区：

| Agent | 责任 |
| --- | --- |
| Claude | 只读分析，不改文件 |
| Codex | 只改指定目录 |
| Kimi | 整理文档和任务清单 |
| Hermes | 记录状态和串流程 |

### 3. 把排版当最后一步的小事

排版不是小事。

尤其是公众号。

读者不是在看你的 Markdown。

读者是在手机屏幕上看一篇文章有没有节奏、有没有呼吸、有没有质感。

技术文章也一样。

越技术，越需要排版救阅读体验。

## 十三、我会怎么配置这套工作室

如果今天让我从零搭，我会这样来：

| 模块 | 我的选择 |
| --- | --- |
| 主控 | Hermes |
| 主模型 | Kimi K2.6 |
| 架构判断 | Claude Code |
| 代码执行 | Codex |
| 内容初稿 | Kimi + Claude 把关 |
| 公众号排版 | 白底暗金杂志版 inline HTML |
| 草稿箱 | Chrome 登录态 + AppleScript + 内部接口 |
| 通知 | 飞书通知 appMsgId |

这不是最炫的配置。

但它比较像能每天用的配置。

我现在对 AI 工具的判断越来越简单：

能不能形成闭环。

只会回答，不够。

能写初稿，也不够。

能从选题、写作、审核、排版、入草稿、通知、复盘一路跑通，才真的有生产力。

## 十四、最后给你一条启动 Prompt

你可以把这段丢给 Hermes，作为项目启动规则：

```text
你是我的 AI 工作流总控。

请按以下分工执行：

1. Hermes 负责总控、工具调用、记忆、技能和流程编排。
2. Kimi K2.6 作为主模型，负责长上下文、任务拆解和批量执行。
3. Claude Code 负责复杂判断、架构分析、重构风险和内容质量把关，默认只读。
4. Codex 负责具体代码修改、测试修复和 PR review。
5. 多 agent 并行时，必须先划分文件责任区，避免冲突。
6. 公众号文章必须先进入初稿池，人工审核通过后再升级母版。
7. 入公众号草稿箱前，必须带图，并渲染成白底暗金杂志版 inline HTML。
8. 不读取 secrets、token、cookie、.env，除非我明确要求。

现在请只读当前项目，输出：
- 项目是什么
- 当前技术栈
- 最适合 Claude 分析的 3 个问题
- 最适合 Codex 执行的 3 个任务
- 最适合 Kimi 长时间执行的 3 个任务
- 如果要发公众号，应该如何进入初稿池和草稿箱流程
```

这条 prompt 的重点不是“让 AI 干活”。

而是先把工位摆好。

工位摆好以后，AI 才不是一堆窗口。

它才像一个工作室。

而 Hermes，就是这个工作室里那个穿得最体面、到处递信、调度所有人的“爱马仕”。

说实话，这个比单纯追新模型有意思多了。

祝顺！
