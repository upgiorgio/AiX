为什么不建议立刻把整套流程重写成 LangGraph？
LangGraph 的 checkpoint、HITL 和 time travel 很适合长任务，但现有系统的首要问题是数据契约和故障边界。先用 SQLite `runs / stages / artifacts / errors` 四张表即可获得 80% 的可恢复价值。等到跨模型并行、长任务恢复和人工中断成为常态，再把相同状态机迁移到 LangGraph，避免框架先于问题。
多 Agent 什么时候值得用？
Anthropic 的生产经验显示，多 agent 对“多个相互独立方向的广度型研究”有效，但 token 成本显著更高。建议只用于高价值深度选题：例如同时查产业链、竞品、海外讨论、论文与本地案例；每日 RSS 归并、去重、评分、排版继续走确定性 DAG。
2026-07-10 核验到的关键版本
MCP 稳定版 2025-11-25、2026-07-28 RC；OpenAI Agents SDK Python v0.18.0；LangGraph 1.2.8；Promptfoo 0.121.18；Ragas 0.4.3；LangSmith SDK 0.10.1。所有快速迭代依赖都应精确 pin 版本，并在升级前跑固定回归集。
03

目标架构：一条不可变信号流，三次人工决策

三个明确的人类节点分别是：是否进入候选池、是否进入起稿、是否进入草稿箱。其余步骤自动化并保留 trace。

01 INGEST采集适配器RSS / X / GitHub / HN / Bluesky / OpenAlex
02 NORMALIZE统一事件账本canonical URL / hash / 时间 / 权利
03 CLUSTER事件聚类exact + SimHash + embedding + mechanism
04 SCORE选题组合价值评分 + MMR 多样性 + 配额
05 RESEARCH证据包claims / sources / counterpoints / risks
06 DRAFT写作与评测结构输出 / trace / regression dataset
07 COMPILE多渠道编译WeChat / Web / social card / approval / receipt

每个节点写入 `run_id + stage + input_hash + output_hash + status + latency + cost + error_class`，失败后从最近成功 checkpoint 恢复。

HUMAN GATE A

候选池放行

只看 8–12 个聚类后的事件卡，不看 200 条原始素材。允许“保留观察”，不要求立刻起稿。

HUMAN GATE B

起稿放行

检查核心机制、证据级别、个人桥与同月选题组合。一次选择 1–3 篇。

HUMAN GATE C

草稿箱放行

检查标题、来源风险、版面快照和微信往返结果。草稿箱不等于公开发布。

微信推送超时为什么不能直接重试？
这是有外部副作用的步骤：远端可能已创建草稿，但客户端没有拿到响应。遇到 ambiguous 状态，必须先查草稿箱，按标题、内容 hash 或稳定指纹 reconciliation；找到后补记 appMsgId，无法确认则暂停人工处理。只有“草稿已创建 + appMsgId”才算成功，不能盲重试制造重复草稿。

X 热度必须改成相对指标。

同时必须遵守 X 的接入边界。

05

选题不是排行榜，是每天的内容投资组合

先对单个候选评分，再用 MMR 做组合去重，最后施加品类配额。这样可以同时解决“都很热但都在讲同一件事”和“换标题重复同一机制”。

BaseScore = 20×证据 + 18×账号匹配 + 16×机制新颖 + 14×新鲜度 + 14×可执行/商业性 + 8×讨论速度 + 6×个人桥 + 4×可复用资产 − 风险罚分
PortfolioPick = λ×BaseScore − (1−λ)×maxSimilarity(已选题)　　建议 λ = 0.68

DAILY PORTFOLIO

四个选题槽位

  • 快信号24–72h；至少 2 个独立来源；回答“今天为什么值得写”。
  • 结构题7–30 天；同类事件聚类；回答“背后的因果机制是什么”。
  • 机会题明确谁付钱、成本、毛利、门槛、竞争者和停止条件。
  • 长青题论文、历史、行业底层规律；不伪装成即时新闻。

每日 shortlist 8–12 个，起稿 1–3 个。任何单一 category 不超过当日入选的 40%；至少 1 个非 AI 题，至少 1 个有可核算商业结构的题。

新颖性为什么要分成“叙事相似”和“机制相似”？
同一机制可以换很多标题、场景和词汇，单纯 embedding 会漏掉“换皮重复”；反过来，两篇文章可能使用相近词汇，却回答完全不同的因果问题。建议保留现有 lexical + embedding，并新增 `mechanism_id / causal_chain`：例如“信息缺席”“评分表外包”“精度预算”作为机制层标识。组合选择时分别惩罚叙事相似和机制重复。
候选被判疑似幻觉时如何处理？
把候选状态改为 `quarantined`，记录失败的 claim 或 title token，继续让其余候选进入选题库。只有当整批来源文件损坏、schema 解析失败或来源时间不可信时才阻断整个 batch。人工修复后可从 quarantine 单条重放。
06

“抓文章”升级为带权利边界的内容事件

默认保存元数据、摘要、证据片段和哈希；只有公开且允许保存的内容才保留全文。付费墙、私密群、主账号 Cookie 和绕过权限不进入自动化默认路径。

LAYER 1

Raw Event

原始响应或最小快照，append-only；记录抓取器、时间、HTTP 状态、etag、原始 hash。

LAYER 2

Normalized Item

统一标题、作者、canonical URL、发布时间、语言、正文摘要、权利与公开范围。

LAYER 3

Evidence Pack

主张、来源、证据片段、反证、实体、机制、风险与候选选题之间的引用关系。

TOKEN MODEL

颜色、章法、渠道三维正交

foundation 保存颜色/字号/间距；semantic 保存正文/弱文字/强调；component 保存 quote/table/hero；6 个 palette 只覆盖颜色；3 个 motif 是结构 recipe；channel 只定义平台约束。避免复制 18×渠道套模板。

IMPORTANT CORRECTION

现有自检更像 denylist

当前禁用项扫描不能被称为完整“白名单”。新编译器必须逐个解析 style declaration，把属性分成 verified-safe、verified-stripped、unknown；生产环境默认阻断 unknown，并继续做真实微信往返。

DTCG 与 Style Dictionary 的实施边界
DTCG 2025.10 已是稳定社区格式，但不能假设 Style Dictionary 已完整实现 Resolver Module。P0 使用明确、可测试的 merge order，并生成三份产物：Web CSS variables、微信静态 JS token map、卡片 TypeScript object。等完整兼容成熟后再迁移 modifier / resolver。
章法选择由内容特征决定，hash 只作平局。

数据/表格密集优先 classic；叙事/观点型优先 centered；教程/行动清单优先 kicker。生产必须允许显式 override。测试注入固定 `date/seed/font/browser`，否则“标题 + 当天”会让截图每日漂移。

视觉回归的最小测试矩阵

为什么 Juice 不能替代微信兼容验证？
Juice 只负责把 CSS 规则内联到元素，不知道微信会剥除哪些属性、节点和 URL。正确顺序是：组件 CSS → Juice → HTML 节点 allowlist → style 属性/值 allowlist → 空装饰节点与图片检查 → 微信 ProseMirror 往返 → 归一化节点、样式签名和截图对比。
